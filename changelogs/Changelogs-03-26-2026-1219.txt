Config Overhaul Report
Timestamp: 03-26-2026 12:19 (Asia/Singapore)
Scope: config.py only

1. Codebase Analysis Summary

The full Python surface was reviewed before changing the configuration:

- main.py drives the outer bot loop, logging, hotkeys, and embedded regression tests.
- bot.py owns the state machine, priority interrupt system, capture cache, oscillating search, asset handling, adaptive tuning, vision optimizer, and historical learner.
- image_matcher.py owns template loading, red-icon gating, color similarity checks, and asset directory scanning.
- mouse_controller.py owns click timing, cursor stabilization, drag timing, rapid-click scheduling, and forbidden-zone safety checks.
- window_capture.py owns PrintWindow-based capture and crop sizing.
- telegram_notifier.py and get_chat_id.py are auxiliary and were not modified.

The hot paths that actually respond to config.py are:

- FIND_RED_ICONS
- SCROLL via OscillatingSearcher
- SEARCH_UPGRADE_STATION
- HOLD_UPGRADE_STATION
- UPGRADE_STATS
- CHECK_NEW_LEVEL / TRANSITION_LEVEL
- MouseController click and drag timing
- VisionOptimizer and HistoricalLearner bounds

2. Root Causes Found

Root cause A: multiple timing surfaces were effectively zeroed out.

The bot had zero or near-zero values for:

- CLICK_DELAY
- MOUSE_MOVE_DELAY
- MOUSE_DOWN_UP_DELAY
- MAIN_LOOP_DELAY
- STATE_DELAY
- many state minimum intervals
- pre-click validation delays
- transition delays

That allowed handlers to re-enter almost immediately after visual or input actions, which increases the chance of scanning frames before the UI has settled.

Root cause B: the scroll search widened too aggressively.

The previous search profile used:

- SCROLL_PIXEL_STEP = 150
- MAX_SCROLL_CYCLES = 4
- SCROLL_INCREMENT_STEP = 3
- very small settle / pause values

That meant the exploration pattern could cover a lot of vertical distance quickly, increasing the risk of moving past assets between stable scans.

Root cause C: the AI speed-learning model was mostly pinned.

Adaptive and historical learning existed in code, but most of its useful timing ranges were functionally disabled because:

- click delay min/max were both 0.0
- move delay min/max were both 0.0
- adaptive click/move step values were 0.0

This prevented the bot from behaving like a cautious beginner that gradually becomes faster and cleaner over time.

Root cause D: the red-icon HSV gate was slightly too strict for the shipped asset set.

Verification on the asset pack showed:

- RedIcon12.png had 52 valid red pixels
- config required 54

This created a real false-negative risk against one of the bot’s own templates.

Root cause E: transition and monitor timing were too aggressive.

The level-complete path used zero delays for:

- NEW_LEVEL_BUTTON_DELAY
- NEW_LEVEL_FOLLOWUP_DELAY
- TRANSITION_POST_CLICK_DELAY
- TRANSITION_RETRY_DELAY

That can cause click sequences to outrun the game’s transition animation and acknowledgement flow.

3. What Changed

3.1 Detection and Asset Scanning Stability

- Aligned TEMPLATES_DIR to the real asset directory used by the project.
- Lowered RED_ICON_PIXEL_THRESHOLD from 54 to 50 so every shipped red icon asset passes the HSV gate.
- Slightly relaxed the primary vision thresholds while keeping all existing color and template gates active:
  - MATCH_THRESHOLD
  - RED_ICON_THRESHOLD
  - NEW_LEVEL_RED_ICON_THRESHOLD
  - STATS_RED_ICON_THRESHOLD
  - UPGRADE_STATION_THRESHOLD
  - BOX_THRESHOLD
  - UNLOCK_THRESHOLD
  - NEW_LEVEL_THRESHOLD
- Slightly relaxed red dominance requirements:
  - RED_ICON_COLOR_MIN_RATIO
  - RED_ICON_COLOR_MIN_MEAN
- Slightly relaxed upgrade-station HSV ratio:
  - UPGRADE_STATION_HSV_MIN_RATIO

Net effect:

- detection remains strongly gated
- one real asset false negative was removed
- runtime scans have slightly more tolerance without opening the door to loose template-only clicking

3.2 Scroll Cycle and Search Cadence

The search profile was rebuilt to widen more deliberately:

- SCROLL_PIXEL_STEP: 150 -> 136
- MAX_SCROLL_CYCLES: 4 -> 6
- SCROLL_INCREMENT_STEP: 3 -> 1
- SCROLL_INTERVAL_PAUSE: 0.010 -> 0.018
- POST_SCROLL_SETTLE: 0.078 -> 0.094
- CYCLE_PAUSE_DURATION: 0.018 -> 0.040
- SCROLL_DURATION: 0.24 -> 0.27
- SCROLL_STEP_COUNT: 24 -> 28
- SCROLL_MIN_INTERVAL: 0.0 -> 0.012
- OSCILLATION_CYCLE_COOLDOWN: 0.0 -> 0.03
- SCROLL_SETTLE_DELAY: 0.012 -> 0.018

Net effect:

- the bot scrolls shorter distances per unit
- the widening pattern is gentler
- every drag is given more time to visually settle before the next scan
- search remains efficient because the bot still widens across multiple cycles instead of stalling in place

3.7 Progressive Learning Model

The learning system now has real movement instead of zero-width ranges.

Adaptive tuner:

- alpha reduced slightly to smooth reactions
- click delay steps enabled
- move delay steps enabled
- search interval step/decrement rebalanced
- click and move min/max ranges opened
- search interval min/max widened around a cautious baseline

Historical learner:

- save interval increased modestly
- record limit increased
- thread interval increased
- pair window increased from 2 to 3
- batch window increased from 8 to 10
- EMA alpha reduced from 0.38 to 0.22
- minimum improvement ratio increased
- apply cooldown increased
- click, move, and search learning ranges opened

Net effect:

- first runs are steadier and more conservative
- the bot can now actually graduate toward faster click/move/search pacing
- learning is less twitchy and less likely to overfit one lucky completion

4. Intentional Constraint Handling

One important limitation was handled deliberately:

The current code records and stores upgrade_click_interval inside the learner, but the real upgrade spam-click runtime path uses SPAM_CLICK_DELAY directly from config instead of the tuner’s upgrade_click_interval.

Because this task was restricted to config.py only, I did not fake adaptive upgrade-burst behavior by widening upgrade interval learning ranges that the runtime would never consume.

Instead:

- UPGRADE_CLICK_INTERVAL was aligned to the stable spam baseline
- adaptive upgrade interval step/decrement stayed fixed at 0.0
- learning upgrade interval min/max stayed pinned to the same stable value

This avoids giving the appearance of AI learning in a path that is not actually wired to runtime execution.
